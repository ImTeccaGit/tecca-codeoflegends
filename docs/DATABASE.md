# Local database (SQLite)

TECCA CODEOFLEGENDS stores all data on the device, in a single SQLite file
managed **only** by the Rust backend. The frontend never accesses the file.

## 1. Location

| Item | Path |
| --- | --- |
| Database | `%APPDATA%\com.tecca.codeoflegends\tecca-codeoflegends.sqlite3` |
| Temporary WAL files | Same folder, suffixes `-wal` and `-shm` |
| Backups | `%APPDATA%\com.tecca.codeoflegends\backups\` |
| Technical logs | `%LOCALAPPDATA%\com.tecca.codeoflegends\logs\` |

The exact path can be seen and copied from **Settings → Local database**.
The folder depends on the identifier `com.tecca.codeoflegends`, not on the app
name: renaming the product neither moves nor loses the data.

## 2. Creation and opening

At startup (`Database::open` in `src-tauri/src/db.rs`):

1. creates the folder, if missing;
2. opens the file (creating it if missing) with `journal_mode = WAL`,
   `foreign_keys = ON` and `busy_timeout = 5000`;
3. **checks compatibility**: if the file has a newer schema than this version
   knows, i.e. it was created by a later release, opening is refused
   **without changing anything**;
4. **backs up before migrating**: if the database exists and the schema is
   older, it creates a verified backup (`pre-migration`);
5. applies the missing migrations, each in a transaction;
6. records the startup in the activity log and keeps only the last 200 events.

If a step fails, the app **stays open in degraded mode**: every feature that
uses the database shows a clear error with the log path, while the technical
detail goes to the log file. No fallback pretends to succeed.

## 3. Migrations

- Append-only files in `src-tauri/migrations/`, listed in order in
  `MIGRATIONS` (`db.rs`). The schema version is in `PRAGMA user_version`.
- A released migration is **never changed**: every change is a new file plus a
  new entry in the list.
- Each migration runs in `BEGIN … COMMIT` together with the `user_version`
  update; on error a `ROLLBACK` happens and the database stays at the previous
  version.
- Tables are `STRICT`. Timestamps are ISO 8601 UTC generated by SQLite.

| Version | Migration | Content |
| --- | --- | --- |
| 1 | `0001_init` | Settings, champions, builds, runes, matches, notes, activity log |
| 2 | `0002_defaults` | Default settings values |
| 3 | `0003_data_dragon_catalog` | Data Dragon catalog versioned per patch |
| 4 | `0004_user_champion_lanes` | Favorites and lanes chosen by the user (lanes no longer used by the UI) |
| 5 | `0005_jungle_training` | Jungle training routes and attempts |
| 6 | `0006_riot_player_data` | Players, rank, match-v5 matches, saved profiles |
| 7 | `0007_match_analysis` | Damage taken and bans; backfill from `raw_json` |
| 8 | `0008_client_source` | Source of each match (`riot-api` or `league-client`) and last client read |
| 9 | `0009_global_stats` | Opt-in champion statistics: settings, seed players, compact Solo/Duo matches, participants and bans |
| 10 | `0010_global_timeline` | Skill order, starting items and purchases from the match-v5 timeline; copy of the user's own matches (`seed_tier = 'PERSONAL'`) |

## 4. Persistence

These are saved and survive restarts and app updates:

- settings (region, animations, Live detection, overlay, automatic account
  from the client, League folder, Riot ID seen in game, statistics collection);
- Data Dragon catalog;
- favorites;
- jungle routes and attempts;
- Riot profiles and matches;
- collected champion statistics (last 3 patches);
- activity log.

API keys are **not** in the database: they are in the Windows Credential
Manager (see `RIOT_COMPLIANCE.md`).

Uninstalling does **not** delete the data folder, unless you select the
uninstaller option that deletes the application data.

## 5. Backups

| Type | When |
| --- | --- |
| `pre-migration` | Automatic, before updating the schema of an existing database |
| `manual` | **Settings → Database backup → Create backup now** |

- The backup uses `VACUUM INTO`: a consistent, compact copy, created even while
  the app is in use.
- Each copy is reopened read-only and checked with `PRAGMA integrity_check`; a
  corrupted copy is deleted and reported.
- File name: `tecca-codeoflegends-<type>-<YYYYMMDD-HHMMSSmmm>-v<schema>.sqlite3`.
- The last **10** backups are kept; older ones are removed.

### Restore (manual, on purpose)

The app never overwrites the database in use by itself. To restore:

1. close TECCA CODEOFLEGENDS;
2. in `%APPDATA%\com.tecca.codeoflegends\` rename
   `tecca-codeoflegends.sqlite3` (for example to `…-old.sqlite3`) and remove
   any `-wal` and `-shm` files;
3. copy the chosen backup from `backups\` into the folder and rename it
   `tecca-codeoflegends.sqlite3`;
4. restart the app. If the backup has an older schema it is migrated
   automatically, after a new backup.

A backup created by a **newer** version of the app does not open with an older
version: that is the compatibility check of point 2.

## 6. Tests

In `src-tauri/src/db.rs`, `backup.rs` and the module tests, always on
temporary files and never on the real database:

- creating a new database with default values;
- persistence after reopening, without running migrations again;
- settings validation;
- pre-migration backup from a v6 schema and no backup for a new database;
- refusing a database created by a newer version, left untouched;
- verified, readable manual backup, rotation at 10 files, foreign files
  ignored;
- migration 0007 backfill.
